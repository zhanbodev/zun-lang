1. 认识 Zun

Zun 是一门面向独立开发者的脚本语言，强调“从想法到可运行结果”的路径尽量短。

它当前的用户主线很明确：

  • 写脚本
  • 组织模块
  • 使用标准库
  • 直接暴露简单 HTTP 服务

这也是本套 Guide 的组织方式。

这套 Guide 怎么读

这组文档分成三层：

  • Guide：按学习路径展开，讲如何使用 Zun
  • Reference：按主题查表，适合已经入门后回查
  • Spec：记录当前实现行为，遇到边界问题以 Spec 和实现为准

如果你第一次接触 Zun，建议按本 Guide 从前往后读。

Zun 的几个核心特征

1. 符号化语法

Zun 使用 $ 前缀组织大量语言结构：

$ value = 1;
$@ NAME = "zun";
$>> value;

常见形式包括：

  • $ 变量声明
  • $@ 常量声明
  • $fn 函数
  • $# 返回
  • $if、$while、$for 控制流
  • $mod 模块导入
  • $GET、$POST 等 HTTP 路由

2. 默认解释执行

你可以直接运行 .zun 文件，也可以进入 REPL 快速验证代码。

3. 默认动态，支持渐进类型

不写类型注解时，变量保持动态。

$ x = 1;
x = "hello";

写了类型注解后，Zun 会对赋值进行约束：

$ x: Int = 1;

4. 模块、标准库、HTTP 是主线能力

Zun 不只是“能写表达式”的玩具语言。当前实现已经具备：

  • 语言模块系统
  • std.* 标准库模块
  • package.toml 项目配置
  • zun serve HTTP 服务模式

为什么 Zun 长这样

旧 guide 里有一个很重要的点，新主线也应该保留：Zun 不是想做“更大、更全”的通用语言，而是想把独立开发者最常见的起步路径压短。

可以把它理解成：

  • 少一点工程铺垫
  • 少一点框架前置学习
  • 多一点脚本即服务的直接路径

$ 的设计直觉

$ 不只是一个视觉符号，它是 Zun 语法风格的中心。

$ value = 1;
$@ PI = 3.14;
$>> value;

这种写法有两个直接效果：

  • 代码外形很容易识别
  • 初学者更容易把“声明、输出、控制结构”区分开

目标用户

按当前定位，Zun 更偏向这些用户：

  • 独立开发者
  • 需要快速验证 API 或脚本想法的人
  • 不想先搭完整框架再开始的人

和 PHP 式传统 Web 路线的区别

旧文档里有一句比喻是有效的：PHP 更像建房子，Zun 更像先把摊摆出来。

这不是说工程化不重要，而是说 Zun 当前阶段更强调：

  • 今天学
  • 今天写
  • 今天跑起来

当前阶段的方向

从现有文档和实现看，Zun 的方向更接近：

  • 脚本
  • 小型工具
  • 轻量 API
  • 配置驱动服务

而不是一开始就进入重框架、重工程、重生态的路线。

当前适合用 Zun 做什么

按当前实现，比较合适的场景有：

  • 小脚本
  • 配置驱动的小工具
  • 简单文件与环境变量处理
  • 轻量 JSON 处理
  • 原型 API 或内部接口

这一阶段不应该期待什么

Guide 不会把这些内容写成“已经成熟可用”：

  • 完整第三方包生态
  • 大型工程化框架
  • 尚未固定下来的语法提案

2. 安装与 CLI

这一章介绍如何构建 Zun，并理解它当前的几个主要命令入口。

安装

如果你在源码仓库中工作，可以直接本地编译：

git clone https://github.com/zhanbodev/zun-lang.git
cd zun-lang
cargo build --release

可选地把二进制加入 PATH：

export PATH="$PATH:$(pwd)/target/release"

CLI 总览

当前 CLI 主入口包括：

  • zun
  • zun run <file>
  • zun serve [path]
  • zun test [options]

进入 REPL

不带参数启动时，进入 REPL：

zun

你可以在里面直接执行语句：

>> $>> "Hello!";
Hello!
>> $ x = 1 + 2;
>> $>> x;
3

退出 REPL 的常见方式：

  • 输入 exit
  • 输入 quit
  • 在空输入时按 Ctrl+D

常见快捷操作：

  • ↑ / ↓ 查看历史记录
  • Ctrl+A 跳到行首
  • Ctrl+E 跳到行末
  • Ctrl+C 取消当前输入
  • Ctrl+D 在空行时退出

运行单个文件

运行 .zun 文件：

zun run hello.zun

run 当前要求传入 .zun 文件路径。

启动服务模式

服务模式用于加载 HTTP 路由并启动服务：

zun serve .

也可以直接指定脚本文件或项目目录：

zun serve main.zun
zun serve .

打印路由表：

zun serve . --routertab

测试模式

HTTP 测试入口：

zun test
zun test main.zun

测试某条指定路由：

zun test --route GET /hello

给 POST / PUT 之类的请求附带 body：

zun test --route POST /users --body '{"name":"Tom"}'

命令和运行模式的关系

可以把 CLI 理解成四种工作模式：

  • REPL：交互试验
  • Run：执行脚本
  • Serve：启动 HTTP 服务
  • Test：对路由进行测试

其中 serve 和 test 会更多地涉及项目配置、HTTP 路由和模块加载。

一个建议的上手顺序

第一次使用时，建议按这个顺序：

  1. 先进入 zun 试几行表达式
  2. 再用 zun run hello.zun 跑单文件
  3. 再用 zun serve main.zun 启动一个最小路由
  4. 最后再看 zun test

3. 第一个程序

这一章只做三件事：跑第一个脚本、试一次 REPL、起第一个 HTTP 路由。

第一个脚本

创建 hello.zun：

$>> "Hello, Zun!";

运行：

zun run hello.zun

怎么确认成功

  • 终端应该输出 Hello, Zun!
  • 如果没有输出，先检查语句末尾是否有分号
  • 如果提示找不到文件，确认你在 hello.zun 所在目录执行命令

第一个 REPL 交互

进入 REPL：

zun

输入：

>> $ name = "builder";
>> $>> f"hello, {name}";
hello, builder

REPL 适合做这些事情：

  • 试表达式
  • 试字符串与列表方法
  • 快速复现小问题

第一个 HTTP 路由

创建 main.zun：

$GET("/hello") hello() -> String {
    $# "world";
}

启动：

zun serve main.zun

怎么确认成功

先看终端没有报错，再用浏览器或 curl 验证：

curl http://127.0.0.1:8080/hello

预期结果：

  • 响应体是 world
  • 如果你改了 [server] 端口，就把 8080 换成对应端口
  • 浏览器直接访问 http://127.0.0.1:8080/hello 也应看到同样结果

单文件和项目目录的区别

单文件适合：

  • 小脚本
  • 小型 demo
  • 单路由接口

项目目录适合：

  • 需要 package.toml
  • 需要多个模块
  • 需要统一 server 配置

项目目录的入口、entry 和 $main() 在 12-projects-and-package.md 里详细说明。

4. 基本语法

这一章不是“扫一眼语法名词”，而是先把 Zun 程序最常见的组成方式讲清楚。读完这一章，你应该已经能看懂大部分简单脚本。

语句与分号

Zun 的普通语句通常以 ; 结束：

$ value = 1;
$>> value;

块语句使用 { ... } 组织。

$if true {
    $>> "in block";
}

可以先记住一个简单规则：

  • 普通语句通常以 ; 结束
  • 带代码块的语句用 { ... }
  • 函数、条件、循环、HTTP 路由都会用到代码块

注释

单行注释：

// comment
$ value = 1;

多行注释：

/* multi
line */
$>> "ok";

注释不会参与执行，适合：

  • 解释一段逻辑
  • 临时屏蔽一小段代码
  • 给示例加说明

标识符与 $ 前缀关键字

Zun 中很多语言结构都带 $ 前缀：

$ value = 1;
$@ NAME = "zun";
$fn greet(name) -> String {
    $# f"hi {name}";
}

其中：

  • $ 用来声明变量
  • $@ 用来声明常量
  • $fn 用来声明函数
  • $# 用来返回值

不要把它们当作普通变量名的一部分，它们本身就是语法关键字。

常见字面量

$ n = 42;
$ f = 3.14;
$ s = "hello";
$ c = 'a';
$ b = true;
$ empty = null;

数字

整数和浮点数都可以直接写：

$ a = 42;
$ b = -7;
$ c = 3.14;

字符串

字符串使用双引号：

$ name = "Zun";
$>> "hello";

支持常见转义：

$>> "line1\nline2";
$>> "tab\tvalue";

字符

字符使用单引号：

$ ch = 'a';
$>> ch;

布尔与 null

$ ok = true;
$ failed = false;
$ empty = null;

f-string

$ name = "Zun";
$>> f"Hello, {name}";

f"..." 允许把表达式插入字符串中：

$ score = 100;
$>> f"user={name}, score={score}";
$>> f"1 + 2 = {1 + 2}";

这在打印调试信息时尤其常用。

列表与 map 字面量

列表

$ nums = [1, 2, 3];
$ names = ["tom", "jerry"];
$ mixed = [1, "two", true];

map

$ user = {"name": "Tom", "age": 25};
$ settings = {"debug": true, "port": 8080};

map 的 key 当前最常见写法是字符串 key。

表达式

当前常见表达式包括：

  • 数字、字符串、布尔、字符、null
  • 列表字面量
  • map 字面量
  • 变量读取
  • 函数调用
  • 方法调用
  • 索引访问
  • 一元与二元运算

下面把这些表达式逐个看一遍。

1. 变量读取

$ value = 10;
$>> value;

2. 函数调用

$fn add(a, b) -> Int {
    $# a + b;
}

$>> add(1, 2);

3. 方法调用

$ text = " hello ";
$>> text.trim();
$>> text.type();

4. 索引访问

$ items = ["a", "b", "c"];
$>> items[0];

$ user = {"name": "Tom"};
$>> user["name"];

5. 一元运算

$>> -3;
$>> !false;

6. 二元运算

$>> 1 + 2;
$>> 5 - 3;
$>> 4 * 2;
$>> 7 / 2;
$>> 7 % 3;
$>> 1 < 2;
$>> 1 == 1;
$>> true && false;
$>> true || false;

一个综合例子

$ user = {"name": "Zun", "scores": [90, 95, 100]};
$ first = user["scores"][0];
$ name = user["name"];
$>> f"{name} first={first}";

这个例子里同时出现了：

  • map 字面量
  • 列表字面量
  • 索引访问
  • 变量读取
  • f-string

最小优先级直觉

$>> 1 + 2 * 3;

结果是 7，不是 9，因为乘除优先于加减。

再看几个例子：

$>> (1 + 2) * 3;
$>> !false && true;
$>> [1, 2, 3].len();

可以先记住这几个最重要的规则：

  • () 可以强制改变计算顺序
  • * / % 优先于 + -
  • 比较运算在算术运算之后
  • 方法调用与索引访问会紧跟在主表达式后面继续解析

5. 值、变量与常量

这一章把“怎么存值、改值、打印值、读入值”讲完整。写 Zun 脚本时，这些操作会出现得最频繁。

变量

变量使用 $ 声明：

$ name = "Zun";
$ answer = 42;

一个变量名绑定一个值：

$ price = 19.9;
$ enabled = true;

变量可以重新赋值：

$ counter = 1;
counter = counter + 1;
counter += 1;

也就是说，你可以先声明，再更新：

$ total = 0;
total = total + 10;
total += 5;
$>> total;

常量

常量使用 $@ 声明：

$@ APP_NAME = "Zun";
$@ MAX = 10;

常量声明后不能再修改。

常量适合表达这些内容：

  • 不应该被改写的固定值
  • 应用名称
  • 上限值
  • 约定字符串
$@ APP_NAME = "Zun";
$@ MAX_RETRY = 3;

变量和常量怎么选

如果一个值会变化，用变量：

$ counter = 0;
counter += 1;

如果一个值不应该变化，用常量：

$@ API_VERSION = "v1";

输出

标准输出：

$>> "hello";
$>> 42;

你可以输出任意表达式：

$ name = "Zun";
$>> name;
$>> 1 + 2 * 3;
$>> f"hello, {name}";

标准错误输出：

$>>ERR("error");

它适合打印错误和调试信息：

$ path = "missing.txt";
$>>ERR(f"cannot open: {path}");

读入

读取一行输入：

$ name = $<<LINE();

带提示读取：

$ name = $<<LINE("name: ");

你可以把读到的内容继续赋值、打印、传给函数：

$ name = $<<LINE("your name: ");
$>> f"hello, {name}";

这一类读入默认都是字符串输入，后续如果需要数字，可以再做转换：

$ raw = $<<LINE("age: ");
$ age = raw.to_int();
$>> age + 1;

变量遮蔽

同名变量可以再次用 $ 重新声明：

$ value = 1;
$>> value;

$ value = "hello";
$>> value;

这表示你重新定义了一个同名变量，而不是对原值做普通赋值。

当前的值类型直觉

从用户视角，当前最常见的值类型包括：

  • Int
  • Float
  • String
  • Bool
  • List
  • Map
  • Null

可以先有一个最基础的印象：

$ i = 1;
$ f = 3.14;
$ s = "hello";
$ ok = true;
$ items = [1, 2, 3];
$ user = {"name": "Tom"};
$ none = null;

后续第 8 章会专门讲集合和方法，第 9 章会专门讲类型注解。

一个完整例子

$ name = $<<LINE("name: ");
$@ APP = "demo";
$ count = 1;

$>> f"{APP}: hello, {name}";
$>> count;
count += 1;
$>> count;

6. 控制流

这一章介绍 Zun 中“让程序按条件和次数运行”的方式。只会写表达式还不够，能组织流程才算能写脚本。

条件分支

$ score = 75;
$if score >= 90 {
    $>> "A";
} $elif score >= 80 {
    $>> "B";
} $else {
    $>> "C";
}

这个例子说明了三件事：

  • 条件写在 $if 后面
  • 命中分支后执行对应代码块
  • 没命中时落到 $else

再看一个更贴近脚本的写法：

$ name = "zun";
$if name == "zun" {
    $>> "matched";
} $else {
    $>> "not matched";
}

while 循环

$ i = 0;
$while i < 3 {
    $>> i;
    i += 1;
}

$while 的语义是：

  1. 先判断条件
  2. 条件为真时执行循环体
  3. 循环体结束后回到条件判断

它适合“直到某个条件不成立”为止的任务。

loop 无限循环

$ i = 0;
$loop {
    $>> i;
    i += 1;
    $if i >= 3 {
        $break;
    }
}

$loop 没有条件，本身就是无限循环，因此通常要配合 $break 使用。

for-in 遍历

$for item in [1, 2, 3] {
    $>> item;
}

当前实现支持遍历：

  • List
  • Map
  • String

遍历 List

$ nums = [1, 2, 3];
$for n in nums {
    $>> n;
}

遍历 Map

$ user = {"name": "Tom", "age": 25};
$for key in user {
    $>> key;
}

遍历 map 时，当前拿到的是 key。

遍历 String

$for ch in "abc" {
    $>> ch;
}

遍历字符串时，拿到的是单字符字符串。

C 风格 for

$for i = 0; i < 5; i = i + 1 {
    $>> i;
}

可以把它理解成：

  • 初始化：i = 0
  • 条件：i < 5
  • 更新：i = i + 1

它适合“已知循环计数方式”的场景。

break 与 continue

$for i = 0; i < 5; i = i + 1 {
    $if i == 2 {
        $continue;
    }
    $if i == 4 {
        $break;
    }
    $>> i;
}
  • $continue 跳过本轮后续逻辑，进入下一轮
  • $break 直接结束整个循环

exit

exit 会终止当前程序执行链：

$>> "before";
exit;
$>> "after";

写脚本时要谨慎使用，因为它会直接结束流程。

truthy / falsy

条件判断依赖 truthy / falsy 规则。常见 falsy 值包括：

  • false
  • 0
  • 0.0
  • 空字符串
  • 空列表
  • 空 map
  • Null

例如：

$if "" {
    $>> "truthy";
} $else {
    $>> "falsy";
}

$if [] {
    $>> "truthy";
} $else {
    $>> "falsy";
}

更正式的边界以 docs/spec/semantics.md 为准。

一个完整例子

$ items = [1, 2, 3, 4, 5];
$ total = 0;

$for item in items {
    $if item % 2 == 0 {
        $continue;
    }
    total += item;
}

$>> total;

7. 函数

函数是 Zun 组织逻辑、消除重复、拆模块的主要方式。

定义函数

$fn greet(name) -> String {
    $# f"Hello, {name}";
}

调用：

$>> greet("World");

返回值和返回类型

使用 $# 返回：

$fn add(a, b) -> Int {
    $# a + b;
}

没有显式 $# 的函数会返回 Null：

$fn log(msg) {
    $>> msg;
}

当前主线可稳定讲解的返回类型包括：

  • Int
  • Float
  • String
  • Bool
  • List
  • Map
  • JSON
  • HTML
  • Response
  • List<T>，其中 T 可以是内建类型或已定义的用户类型

需要注意的是，当前主线只把 List<T> 当作可教学的泛型返回写法，不把 JSON<T> 当作同级语法来承诺。

参数目前怎么写

当前主线不承诺函数参数类型注解是可用语法。也就是说，这一版文档统一只教下面这种签名：

$fn add(a, b) -> Int {
    $# a + b;
}

如果你需要约束输入，当前推荐做法是：

  • 用返回类型约束输出
  • 在函数体内用 .type()、条件判断或断言做输入检查
  • 在对外接口层用更小的函数拆分而不是依赖参数注解

可变参数

$fn sum(...nums) -> Int {
    $ total = 0;
    $for n in nums {
        total += n;
    }
    $# total;
}

递归

$fn factorial(n) -> Int {
    $if n <= 1 {
        $# 1;
    } $else {
        $# n * factorial(n - 1);
    }
}

私有函数

_$fn normalize(name) -> String {
    $# name.trim().lower();
}

$fn public_name(name) -> String {
    $# normalize(name);
}

_$fn 只给当前模块内部使用。

匿名函数

$ double = $fn(x) {
    $# x * 2;
};

$>> double(5);

一个完整例子

_$fn twice(x) -> Int {
    $# x * 2;
}

$fn compute(n) -> Int {
    $ value = twice(n);
    $# value + 1;
}

$>> compute(10);

8. 集合与常用方法

这一章集中讲三类最常用的值：字符串、列表、Map。重点是“创建、读取、修改、查询”和“什么时候该去 std.*”。

字符串

$ text = "  hello,world  ";
$>> text.trim();
$>> text.upper();
$>> text.split(",");
$>> text.contains("hello");

split() 返回 List，所以可以继续接列表处理：

$ parts = "a,b,c".split(",");
$>> parts.len();
$>> parts.join("-");

列表

$ nums = [3, 1, 4, 1, 5];
$>> nums.len();
$>> nums.contains(4);
$>> nums.index_of(4);
$>> nums.count(1);
$>> nums.slice(1, 4);

常用原地修改方法：

nums.push(9);
nums.sort();
nums.sort_desc();
nums.reverse();

常见读法：

$>> nums.first();
$>> nums.last();
$>> nums.unique();
$>> [[1, 2], [3, 4]].flatten();

索引越界

当前实现里，列表索引越界会报运行时错误，不会返回 null。

例如下面这种写法不应作为主线常规用法：

$ items = [1, 2, 3];
$>> items[10];

更安全的写法是先看长度：

$if nums.len() > 2 {
    $>> nums[2];
}

Map

$ user = {"name": "Tom", "age": 25};
$>> user["name"];
$>> user.len();
$>> user.keys();
$>> user.values();
$>> user.contains_key("age");

Map 写入

当前主线写法直接使用索引赋值：

$ user = {"name": "Tom"};
user["email"] = "tom@example.com";
user["age"] = 25;
$>> user["email"];

删除键：

user.remove("age");

什么时候改用 std.json

如果你操作的是通用 JSON 结构，或者想做“按路径更新、合并、格式化”，优先用 std.json：

$mod std.json;

$ obj = {"name": "Tom"};
$ obj = json.set(obj, "email", "tom@example.com");
$>> json.stringify(obj);

可以把两者这样区分：

  • Map 原生操作：当前变量上的直接读写
  • std.json：更偏通用 JSON 工具和转换函数

值方法和标准库的区别

  • 值方法：nums.push(1)、user.keys()、"a,b".split(",")
  • 标准库：str.trim(text)、json.set(obj, key, value)、math.sqrt(9.0)

如果只是处理当前值本身，先选值方法；如果要做通用转换或组合工具，再去 std.*。

一个完整例子

$ raw = "alice,bob,bob,carol";
$ names = raw.split(",");
names.sort_desc();

$ stats = {"count": names.len()};
stats["unique_count"] = names.unique().len();

$>> names;
$>> stats["count"];
$>> stats["unique_count"];

9. 渐进类型

Zun 当前采用“默认动态，显式约束”的使用方式。

默认动态

不写类型注解时，变量可以改变值类型：

$ x = 30;
x = "hello";
x = true;

显式类型注解

$ count: Int = 0;
$ name: String = "Alice";
$ active: Bool = true;
$ items: List = [1, 2, 3];
$ config: Map = {"name": "demo"};

常量也支持类型注解：

$@ MAX: Int = 100;

当前主线可依赖的声明类型名：

  • Int
  • Float
  • String
  • Str
  • Bool
  • Boolean
  • List
  • Map

当前不要把 Json、Response 写成“变量/常量声明可稳定使用”的类型名。

函数参数类型注解的态度

当前主线文档统一采用保守口径：不教学、不承诺参数类型注解语法。

也就是说，这一版只写：

$fn add(a, b) -> Int {
    $# a + b;
}

如果你需要更强约束，优先使用：

  • 返回类型
  • 局部变量显式声明
  • .type() / std.core.check
  • 10-error-handling.md 里的错误处理方式

返回类型和 List<T>

返回类型是这一章最重要的稳定能力之一。

正确写法

$Type User {
    id: Int
    name: Str
}

$fn list_users() -> List<User> {
    $# [
        {"id": 1, "name": "Alice"},
        {"id": 2, "name": "Bob"}
    ];
}

这里要记住两条：

  • List<T> 是当前主线可用写法
  • 裸 List 不应再作为返回类型写法来教学

T 可以是内建类型，也可以是先定义好的用户类型。

$Type

$Type 用来描述结构，不等于 class：

$Type User {
    id: Int
    name: Str
    email: Str?
}

它最适合和 List<T>、接口返回说明、阅读文档时的结构表达配合使用。

HTTP 返回里的 List<T>

在 HTTP 章节里同样推荐这样写：

$Type User {
    id: Int
    name: Str
}

$GET("/users") list_users() -> List<User> {
    $# [
        {"id": 1, "name": "Alice"},
        {"id": 2, "name": "Bob"}
    ];
}

如果类型或返回校验失败，它会表现为用户可见错误；如何排查请继续看 10-error-handling.md。

运行时类型查询

10. 错误处理

Zun 当前同时有解析错误、运行时错误和显式抛出的异常。

三类错误先怎么分

  • 代码还没跑起来就出错：词法 / 语法错误
  • 跑到一半因为值或环境问题出错：运行时错误
  • 代码里主动抛出：$throw

$try / $catch

$try {
    $throw "oops";
} $catch err {
    $>> err;
}

如果 try 块内部抛错，就会进入 catch 块。

err 到底是什么

在主线文档里，可以先把 err 理解成“可打印、可比较、可继续传递的错误值”。

安全做法：

  • 直接打印 err
  • 把 err 拼进日志字符串
  • 用 err.type() 看当前值类型
  • 根据上下文返回默认值或改写响应

例如：

$mod std.fs;

$try {
    $ content = fs.read_text("missing.txt");
    $>> content;
} $catch err {
    $>>ERR(f"read failed: {err}");
}

主线不把 err 讲成运行时内部结构体，也不承诺固定字段集合。

$throw

$throw "bad input";

适合：

  • 主动拒绝非法输入
  • 在工具函数里显式抛出失败
  • 提前终止一条不该继续的路径

可捕获性速查

场景能否被 $catch 捕获备注
$throw "oops"可以最直接的用法
除零可以运行时错误
未定义变量可以运行时错误
类型不匹配可以运行时错误
文件读取失败可以例如 std.fs.read_text(...)
模块加载失败不作为主线承诺通常发生在装载阶段，优先先修模块路径
语法错误不可以程序尚未进入执行阶段

查表版说明见 ../reference/errors.md。

常见例子

文件读取失败

$mod std.fs;
$try {
    $ content = fs.read_text("missing.txt");
    $>> content;
} $catch err {
    $>> "caught!";
}

环境变量失败

$mod std.env;
$try {
    $ token = env.get("APP_TOKEN");
    $>> token;
} $catch err {
    $>> "env error caught";
}

主动抛错

$fn must_positive(n) -> Int {
    $if n <= 0 {
        $throw "n must be positive";
    }
    $# n;
}

怎么排查

  1. 先分清是 parse error 还是 runtime error
  2. 再看出错位置
  3. 看是语法、值类型、模块、文件还是环境问题
  4. 尽量把问题缩成最小 .zun 文件

11. 模块系统

Zun 通过 $mod 组织可复用代码。脚本一旦开始变大，就应该进入模块拆分。

导入单个模块

$mod shared.helper;
$>> helper.answer();

模块路径使用点号分隔，对应 .zun 文件路径。

命名空间访问

导入后，通过文件名命名空间访问：

$mod helper;
$>> helper.answer();

重点是：不会把函数直接铺平到当前作用域。

通配符导入：$mod math.*;

当前实现支持：

$mod math.*;

它的含义是：

  • 导入 math/ 目录下的直接子模块
  • 把这些子模块注册成命名空间
  • 不会把子模块函数直接平铺到当前作用域

例如：

math/
├── add.zun
└── calc.zun

$mod math.*;
$>> add.answer();
$>> calc.square(3);

不要把它理解成下面这种旧预期：

$mod math.*;
$>> answer();      // 旧预期，当前主线不这样讲

公有函数与私有函数

$fn public_api() -> Int {
    $# 1;
}

_$fn hidden() -> Int {
    $# 2;
}

规则：

  • $fn 默认公开
  • _$fn 默认私有
  • $mod 只暴露公开函数

std.* 命名空间

标准库模块也通过 $mod 导入：

$mod std.math;
$mod std.str;

$>> math.sqrt(16.0);
$>> str.trim("  hello  ");

std.* 是保留命名空间，只走标准库解析，不和普通项目模块混用。

当前模块解析顺序

普通模块的主顺序：

  1. 当前文件所在目录
  2. 当前项目根目录
  3. 项目根目录下的 modules/
  4. 如果声明了依赖，再查 deps/

std.* 则只走标准库解析。

一个完整例子

目录：

demo/
├── main.zun
└── shared/
    └── helper.zun

shared/helper.zun：

_$fn twice(x) -> Int {
    $# x * 2;
}

$fn answer() -> Int {
    $# twice(21);
}

main.zun：

$mod shared.helper;
$>> helper.answer();

其中 [dependencies] 当前更适合理解为模块解析边界的一部分，而不是成熟包管理工作流。

入口文件和 entry

当 CLI 传入目录时：

  1. 先定位项目根
  2. 读取 package.toml
  3. 使用 entry 指定的入口文件
  4. 如果没有 manifest，则默认尝试 main.zun

所以：

  • entry 决定“从哪个文件启动项目”
  • 它不等于 $main()

$main() 什么时候需要

$main() 是 serve 模式下的顶层入口，用来放全局初始化逻辑。

例如：

@CORS("*")
$main() {
    $>> "[INFO] server starting";
}

$GET("/health") health() -> String {
    $# "ok";
}

可以这样理解：

  • 只需要一个简单路由时，可以不写 $main()
  • 需要全局 @CORS、启动日志、启动前准备动作时，再写 $main()
  • entry 负责选入口文件，$main() 负责该文件里的服务入口逻辑

$<<CONFIG(...) 的使用边界

[env] 中的值可以通过 $<<CONFIG(...) 读取：

$ app = $<<CONFIG("APP_NAME");

但要记住：

  • 它依赖项目配置上下文
  • 当前实现里只在 serve 模式下可用
  • 不应把它当成 run 模式下的通用配置入口

推荐的跨模式兜底写法是优先读环境变量，把 CONFIG 留给 serve 项目：

$mod std.env;

$ app = env.get_or("APP_NAME", "My App");
$>> app;

如果你明确只在 serve 项目里运行，再使用 $<<CONFIG(...)。

server 配置

服务模式会读取 [server]：

[server]
host = "0.0.0.0"
port = 8080

执行：

zun serve .

时，CLI 会加载这部分配置。

项目和单文件的区别

单文件适合：

  • demo
  • 小工具
  • 单路由原型

项目目录适合：

  • 多模块
  • 配置读取
  • 服务模式
  • 后续继续扩展

14. I/O、环境变量与配置

这一章把和宿主环境直接交互的能力收在一起：环境变量、项目配置、文件系统。

环境变量

语言表面：$<<ENV(...)

$ home = $<<ENV("HOME");

如果环境变量不存在，这类调用会失败。

标准库：std.env

$mod std.env;
$>> env.get_or("APP_ENV", "dev");

当你需要兜底值时，优先选 env.get_or(...)。

项目配置：$<<CONFIG(...)

$ app = $<<CONFIG("APP_NAME");

当前实现里，它有两个重要边界：

  • 依赖项目配置上下文
  • 只在 serve 模式下可用

也就是说，在 run 模式里把它当成通用配置读取入口会直接报错。

推荐的跨模式写法

如果你希望脚本和服务都能运行，先用环境变量作为兜底主路径：

$mod std.env;

$ app = env.get_or("APP_NAME", "My App");
$>> app;

如果某段代码只在服务项目里运行，再使用 $<<CONFIG(...)。

文件读取：$<<FILE(...)

当前语言层面可写的形式是：

$ text = $<<FILE("notes.txt");
$ lines = $<<FILE("notes.txt", "LINES");

口径统一如下：

  • $<<FILE(path)：读取全文，结果按文本处理
  • $<<FILE(path, "LINES")：按行读取
  • 第二个参数当前主线只写 "LINES"，不继续扩展旧文档里的其他模式字符串

std.fs 和 $<<FILE(...) 怎么选

如果你只是想在一行里读一次文件，$<<FILE(...) 足够直观。

如果你需要：

  • 更明确的 API
  • 写入、追加、删除
  • exists、is_dir、list 这类能力

优先用 std.fs：

$mod std.fs;

$ content = fs.read_text("tests/fixtures/stdlib/hello.txt");
$ lines = fs.read_lines("tests/fixtures/stdlib/lines.txt");

可以把两者这样区分：

  • $<<FILE(...)：语言层面的简写入口
  • std.fs.read_text/read_lines(...)：脚本和项目里的主推荐写法

文件写入

$mod std.fs;

fs.write_text("/tmp/zun-demo.txt", "hello");
$>> fs.read_text("/tmp/zun-demo.txt");
fs.delete("/tmp/zun-demo.txt");

常见坑

  • 环境变量不存在会抛错，除非你用 get_or
  • $<<CONFIG(...) 不是跨模式通用入口
  • 文件路径错误会导致运行时错误
  • 有副作用的能力最好配合 $try / $catch

15. HTTP 基础

Zun 当前内置了 HTTP 路由定义能力，可以直接和 zun serve 配合使用。

定义路由

$GET("/hello") hello() -> String {
    $# "world";
}

启动：

zun serve main.zun

handler 的基本形状

一个 handler 一般包含四部分：

  1. HTTP 方法关键字
  2. 路径
  3. 函数名和参数
  4. 返回类型和函数体
$GET("/users/:id") get_user(id) -> JSON {
    $# $JSON { "id": id };
}

返回类型

常见返回类型：

  • String
  • JSON
  • HTML
  • List<T>

List<T> 返回例子

$Type User {
    id: Int
    name: Str
}

$GET("/users") list_users() -> List<User> {
    $# [
        {"id": 1, "name": "Alice"},
        {"id": 2, "name": "Bob"}
    ];
}

这里同样遵守类型章节的口径：返回集合时优先写 List<T>，不要再教学裸 List。

路径参数与 query 参数

$GET("/users/:id") get_user(id) -> JSON {
    $# $JSON { "id": id };
}

query string 会按同名变量注入：

$GET("/search") search() -> JSON {
    $# $JSON { "q": q, "limit": limit };
}

Header 读取

$GET("/whoami") whoami() -> JSON {
    $ token = $HDR("Authorization");
    $# $JSON { "token": token };
}

body 注入

当前主线明确这条规则：

  • POST、PUT、PATCH 会把请求体注入到 body
  • GET、DELETE 不把 body 当作主线能力来承诺

最小例子：

$POST("/echo") echo() -> JSON {
    $# $JSON { "body": body };
}

继续取字段：

$PATCH("/users") patch_user() -> JSON {
    $ name = body["name"];
    $# $JSON { "updated": true, "name": name };
}

HTML 返回

直接内联

$GET("/") index() -> HTML {
    $# $HTML("<h1>Welcome</h1>");
}

链接外部文件：$HTML().link(...)

$GET("/") index() -> HTML {
    $# $HTML().link("pages.index");
}

记法：

  • 使用模块式路径，如 "pages.index"
  • 它对应外部页面资源，而不是 URL path
  • 当前主线把它当作链接外部 HTML/CSS/JS/XML 文件的入口

如果你已经在组织多文件页面或路由模块，继续看 16-http-organization.md。

std.http 客户端

如果你不是在“接收请求”，而是要“调用别的服务”，用 std.http：

$mod std.http;

$ res = http.get("https://example.com");
$>> res["status"];
$>> res["body"];

如果 URL 不合法、连接失败或超时，错误会作为普通运行时错误抛出，可以配合 $try / $catch。

16. HTTP 组织方式

当路由开始增多时，就需要把 HTTP 代码组织起来。

$HTTP { ... }

$HTTP {
    $GET("/ping") ping() -> String {
        $# "pong";
    }

    $GET("/health") health() -> String {
        $# "ok";
    }
}

带前缀的 HTTP 块

$HTTP("/api/v1") {
    $GET("/users") list_users() -> JSON {
        $# $JSON { "ok": true };
    }
}

$main() 的位置

$main() 适合放全局初始化逻辑：

@CORS("*")
$main() {
    $>> "[INFO] server starting";
}

什么时候需要：

  • 需要全局 @CORS
  • 需要启动日志或初始化动作
  • 想把“启动阶段逻辑”和“路由定义”显式分开

什么时候可以省略：

  • 只有少量路由
  • 没有全局初始化逻辑

它和 entry 的关系是：

  • entry 选入口文件
  • $main() 定义该文件里的 serve 入口逻辑

组织 @SET_HDR(...)

@SET_HDR({
    "X-Frame-Options": "DENY",
    "Cache-Control": "no-cache"
})
$HTTP("/api") {
    $GET("/ping") ping() -> String {
        $# "pong";
    }
}

规则：

  • 块级 header 会传给块内路由
  • 同名 header 由更靠近路由的声明覆盖

组织 @CORS(...)

@CORS(...) 可以放在三个层级：

  • $main() 前：全局默认策略
  • $HTTP(...) 前：路由组策略
  • 具体路由前：单条路由策略

优先级：

  • 路由级覆盖块级
  • 块级覆盖全局

链接外部路由模块

$HTTP("/v1/api").link("routers.api");

.link() 只用于挂载 HTTP 路由，不等于普通 $mod 导入。

静态资源和 HTML 文件

$STATIC("/static", "static");

$GET("/") index() -> HTML {
    $# $HTML().link("pages.index");
}

路由冲突怎么处理

当前仓库没有把“同路径同方法重复注册”的底层策略写成稳定主线规则，因此这一章只给出安全建议，不虚构实现细节。

推荐做法：

  1. 同一个路径只在一个文件里定义一次
  2. 先按业务域拆路由，再用 .link() 汇总
  3. 启动时打开 --routertab 或最小化路由文件确认最终注册结果
  4. 排查顺序先看入口文件、再看 .link()、最后看重复路径

如果你怀疑冲突，先把可疑路由缩成最小例子再排查。

一个完整例子

@CORS("*")
$main() {
    $>> "[INFO] server starting";
}

@SET_HDR({ "X-Frame-Options": "DENY" })
$HTTP("/api") {
    $GET("/ping") ping() -> JSON {
        $# $JSON { "ok": true };
    }
}

$HTTP("/site").link("routers.site");
$STATIC("/static", "static");

17. 测试与调试

这一章给一条最实用的工作流：先验证最小功能，再缩小问题面，再做最小复现。

1. 断言与基本验证

最轻量的验证方式仍然是直接运行并看输出：

$fn add(a, b) -> Int {
    $# a + b;
}

$>> add(1, 2);

运行：

zun run main.zun

预期看到：

3

对脚本逻辑来说，先把“输入是什么、输出是什么”写清楚，比一开始就堆复杂测试框架更重要。

如果你想把“预期必须成立”写进代码里，优先用 std.core.check.assert：

$mod std.core.check;

check.assert(1 + 1 == 2, "基础算术失败");

$>> "checks passed";

运行：

zun run test_math.zun

通过时，你会看到：

checks passed

断言失败时，程序会直接报错并停止，这很适合写最小脚本验证。

│   └── helper.zun

当前仓库也可以直接参考：

  • tests/spec/valid/
  • tests/spec/invalid/
  • tests/fixtures/

这些目录最适合看两件事：

  • 最小正确写法是什么
  • 最小错误复现应该缩到多小

最常用命令：

zun test
zun test main.zun
zun test --route GET /hello
zun test --route POST /echo --body '{"name":"Tom"}'

脚本验证路径

对纯脚本逻辑，推荐顺序：

  1. 先 zun run tests/test_xxx.zun
  2. 必要时拆成更小函数
  3. 再把问题缩成最小文件

HTTP 验证路径

对 HTTP handler，推荐顺序：

  1. 先 zun test --route ...
  2. 再 zun serve ... 做真实请求验证
  3. 只在需要时再扩到完整项目路径

4. 终端输出怎么看

一个通过的例子

[OK] GET /hello

一个失败的例子

$ zun run bad.zun
[ERROR] runtime error: variable 'x' not found

遇到失败时，先做三件事：

  1. 看错误类别
  2. 看报错位置
  3. 看是语法、类型、模块、文件还是 HTTP 路由问题

5. 调试工作流

用 REPL 做最小复现

REPL 适合：

  • 试表达式
  • 试类型行为
  • 试字符串和列表方法

用打印定位问题

$>> "debug";
$>> value;
$>>ERR(f"unexpected: {value}");

最适合放打印的位置：

  • 分支判断前后
  • 文件读取之后
  • 返回之前
  • catch 块里

用 $try / $catch 包住不稳定点

$mod std.fs;
$try {
    $ content = fs.read_text("missing.txt");
    $>> content;
} $catch err {
    $>>ERR(f"read failed: {err}");
}

6. 常见排障配方

handler 返回空 body

  • 现象：请求成功，但没有你预期的响应体
  • 检查点：handler 是否真的执行到 $#
  • 推荐动作：先改成最小固定返回，例如 # "ok" 或固定 JSON

模块函数没被调用

  • 现象：程序能跑，但结果像是走了旧逻辑
  • 检查点：是否写了正确的 $mod 路径，是否通过命名空间调用
  • 推荐动作：先在入口处打印模块调用结果，确认不是旧页面里的平铺导入预期

类型注解相关报错

  • 现象：声明或返回时提示类型不匹配
  • 检查点：变量注解是否与实际值一致，返回值是否用了 List<T>
  • 推荐动作：先缩成最小函数，再回看 09-gradual-typing.md 和 10-error-handling.md

核心概念

本文档介绍 Zun 的设计理念和核心概念。

$ 符号哲学

起源

Zun 的诞生，多少带着一点玩的意思。

语言的核心符号是 $ —— 这不是巧合。$ 是全世界最通用的财富符号，美金，财富，钱。我们用它来声明变量、声明常量、打印输出，把每一行代码都和「赚钱」这件事绑定在一起。

写代码，就是赚钱。这是 Zun 最初的态度。

设计理念

Zun 的设计哲学，从第一个符号开始，就为独立开发者服务：

  • $ 声明变量 —— 简单，直接
  • $@ 声明常量 —— 保护重要的东西
  • $>> 打印输出 —— 立刻看到结果
  • 整套语法 6 个符号 —— 今天学，今天用

符号化语法示例

$ a = 1;        // 声明变量
$@ PI = 3.14;  // 声明常量
$>> a;         // 打印输出

这种独特的符号化语法形成了鲜明的视觉风格，让人一眼就能认出这是 Zun 代码。

我们在解决什么问题

PHP 诞生于一个时代：「我要快速搭一个网页」。

那个时代的问题已经被解决了。但时代之后，出现了新的问题，还没有人真正解决：

  • 我不想学框架，我只想快速验证一个 API 想法
  • 我想把一个脚本直接暴露成可调用的服务
  • 我不在乎性能，我在乎的是从想法到跑起来的时间
  • 我想要今天就能开张，而不是明天

这就是 Zun 想卡的位置。

我们和 PHP 不一样在哪里

这个问题值得认真回答，因为表面上我们都在做「快速 Web 服务」。

PHPZun
定位建房子摆摊
目标工程构建变现验证
学习成本需要框架、路由、模板6 个符号，5 分钟上手
时代背景30 年前的 Web独立开发者的今天
态度严肃的工程语言反严肃，追求最快落地

PHP 是建房子的，Zun 是摆摊的。

摆摊不需要地基，不需要设计图纸，需要的是今天就能开张，明天就能收钱。

目标用户

Zun 面向独立开发者——那些同时身兼产品经理、设计师、工程师、运营的人。

他们的时间是稀缺的，他们的耐心是有限的，他们最不需要的就是在「从想法到上线」这条路上多走任何一步弯路。

未来的方向

Zun 目前是一个解释型脚本语言的起点。

我们下一步想做的，是让「变现」这个动作成为语言的一等公民——让支付、Webhook、API 暴露不再是靠第三方库拼凑出来的，而是内建在语言的表达能力里。

我们想要的终态是：

一个 .dal 文件，一条命令，直接是一个能收钱的服务。

这个目标听起来简单，但它需要的不是更复杂的语言，而是更极致的取舍。

一句话总结

Zun 是面向独立开发者的快速变现脚本语言。

$ 不只是变量符号，它是我们对这门语言全部野心的浓缩：

写代码，就是赚钱。

模块解析顺序

当你写 $mod foo.bar; 时，解释器按以下顺序查找：

  1. Native 注册表 — Rust 实现的内置模块（如 std.math、std.fs）
  2. stdlib/ 目录 — 纯 .zun 实现的标准库（如 std.core.iter → stdlib/core/iter.zun）
  3. 项目本地文件 — 当前项目中的 .zun 文件（如 shared.helper → shared/helper.zun）

std 前缀由解释器特殊处理，会映射到标准库目录。

类型注解

Status: Migration Source

这是一页迁移期旧类型文档。 当前主线请改读 09-gradual-typing.md。 本页仍保留的独特价值是旧版示例集合，但其中参数类型注解、JSON<User> 等写法不应视为当前主线承诺。

Zun 支持渐进类型注解：注解完全可选，不影响程序运行，但能提升代码可读性。

变量类型注解

在变量名后加 : 类型 进行注解：

$ count: Int = 0;
$ name: String = "Alice";
$ ratio: Float = 0.5;
$ active: Bool = true;
$ items: List = [1, 2, 3];
$ config: Map = {"key": "value"};

不带注解的写法同样有效：

$ count = 0;
$ name = "Alice";

函数返回类型注解

在参数列表后加 -> 类型：

$fn add(a, b) -> Int {
    $# a + b;
}

$fn greet(name) -> String {
    $# f"Hello, {name}!";
}

$fn is_even(n) -> Bool {
    $# n % 2 == 0;
}

没有返回值的函数可以省略注解：

$fn log(msg) {
    $>> msg;
}

支持的类型名

类型名说明
Int整数
Float浮点数
String / Str字符串
Bool布尔值
List列表
Map字典

自定义类型 $Type

使用 $Type 定义 JSON 数据形状（文档性质，不创建运行时类型）：

$Type User {
    id: Int
    name: Str
    email: Str?    // ? 表示可选字段
    age: Int?
}
  • 字段类型：Int Str Bool Float，首字母大写
  • 可选字段：在类型后加 ?
  • 无 getter / setter，无私有字段，无方法

运行时类型查询

通过 .type() 方法在运行时获取值的类型名：

$>> 42.type();          // Int
$>> 3.14.type();        // Float
$>> "hello".type();     // String
$>> true.type();        // Bool
$>> [1, 2].type();      // List
$>> {"a": 1}.type();    // Map
$>> null.type();        // Null

配合条件判断：

$fn describe(val) -> String {
    $ t = val.type();
    $if t == "Int" {
        $# "这是整数";
    } $else $if t == "String" {
        $# "这是字符串";
    } $else {
        $# f"类型: {t}";
    }
}

$>> describe(42);        // 这是整数
$>> describe("hello");   // 这是字符串

$@ MAX_SIZE: Int = 100;
$@ PI: Float = 3.14159;

Zun 内置 HTTP 服务支持，通过 zun serve 启动，使用声明式语法定义路由。

启动服务

# 运行单文件
zun serve main.zun

# 运行项目目录（自动读取 package.toml）
zun serve .

# 启动并打印路由表
zun serve . --routertab

默认监听 0.0.0.0:8080，可通过 package.toml 修改：

[server]
port = 3000
host = "127.0.0.1"

定义路由

基本语法

$METHOD("/path") handler_name() -> ReturnType {
    // 处理逻辑
    $# 返回值;
}

支持的 HTTP 方法：

关键字HTTP 方法
$GETGET
$POSTPOST
$PUTPUT
$DELDELETE
$PATCHPATCH

示例

$GET("/hello") hello() -> String {
    $# "world";
}

$GET("/ping") ping() -> String {
    $# "pong";
}

返回类型

返回 JSON

$GET("/user") get_user() -> JSON {
    $# {"name": "Alice", "age": 30};
}

返回字符串

$GET("/health") health() -> String {
    $# "ok";
}

返回 HTML

$GET("/") index() -> HTML {
    $# "<h1>Welcome to Zun!</h1>";
}

路径参数

在路径中使用 :param 定义动态参数，参数值自动注入为同名变量：

$GET("/users/:id") get_user(id) -> JSON {
    $# {"id": id, "name": "User " + id};
}

访问 /users/42 → {"id": "42", "name": "User 42"}

请求体（POST / PUT / PATCH）

POST、PUT、PATCH 请求的 JSON body 自动解析，通过 body 变量访问：

$POST("/echo") echo() -> JSON {
    $# body;
}

$POST("/users") create_user() -> JSON {
    $ name = body["name"];
    $ age = body["age"];
    $# {"created": true, "name": name, "age": age};
}

查询参数

URL 查询字符串（?key=value）中的参数自动注入为变量：

$GET("/search") search() -> JSON {
    // GET /search?q=hello&limit=10
    $# {"query": q, "limit": limit};
}

读取请求头

使用 $HDR("Header-Name") 读取请求头：

$GET("/whoami") whoami() -> JSON {
    $ token = $HDR("Authorization");
    $# {"token": token};
}

响应头注解

如果你要给响应统一附加静态 header，用 @SET_HDR(...)：

@SET_HDR({
    "X-Frame-Options": "DENY",
    "Cache-Control": "max-age=3600"
})
$GET("/health") health() -> String {
    $# "ok";
}

规则很简单：

  • @SET_HDR(...) 只接受一个对象字面量
  • key 必须是字符串 header 名
  • value 必须是字符串字面量
  • 一个注解里可以声明多个 header

如果没有写 @SET_HDR(...)，响应不会额外附加这些 header。

CORS 注解

公开接口可以直接写：

@CORS("*")
$GET("/public") public_data() -> JSON {
    $# {"ok": true};
}

需要白名单时，用对象写法：

@CORS({
    origins: ["https://app.example.com"],
    methods: ["GET", "POST"],
    headers: ["Authorization"],
    max_age: 600,
    credentials: true
})
$GET("/profile") profile() -> JSON {
    $# {"ok": true};
}

@CORS(...) 可以放在：

  • $main() 前，作为全局默认策略
  • $HTTP(...) 前，作为块级策略
  • 路由前，作为路由级策略

优先级是路由级覆盖块级，块级覆盖全局；没有写时，就不会额外返回 CORS 响应头。

路由分组（$HTTP 块）

使用 $HTTP("/prefix") { ... } 为一组路由添加统一前缀：

$HTTP("/api/v1") {
    $GET("/users") list_users() -> JSON {
        $# [{"id": 1, "name": "Alice"}, {"id": 2, "name": "Bob"}];
    }

    $POST("/users") create_user() -> JSON {
        $# {"created": true, "user": body};
    }

    $GET("/users/:id") get_user(id) -> JSON {
        $# {"id": id};
    }
}

最终路由为 /api/v1/users 和 /api/v1/users/:id。

链接外部模块路由

将其他模块中定义的路由链接到当前服务，支持多级模块拆分：

// routers/api.zun
$GET("/status") status() -> String {
    $# "running";
}

// main.zun
$HTTP().link("routers.api");

多个模块链接：

$HTTP().link("routers.users");
$HTTP().link("routers.orders");
$HTTP().link("routers.admin");

静态文件

使用 $STATIC 提供静态文件服务：

// 将 /static 映射到项目的 static/ 目录
$STATIC("/static", "static");

// 简写（URL 前缀默认为 /static）
$STATIC("static");

my-app/

读取项目配置

通过 $<<CONFIG("KEY") 读取 package.toml 的 [env] 配置：

# package.toml
[env]
DB_HOST = "localhost"
DB_PORT = "5432"
SECRET_KEY = "my-secret"

$GET("/config") show_config() -> JSON {
    $ db_host = $<<CONFIG("DB_HOST");
    $ db_port = $<<CONFIG("DB_PORT");
    $# {"db_host": db_host, "db_port": db_port};
}

状态码控制

默认情况下，handler 返回 HTTP 200。用 $RES(status, body) 显式指定状态码：

// 404 Not Found
$GET("/users/:id") get_user(id) -> JSON {
    $# $RES(404, {"msg": "用户不存在"});
}

// 201 Created
$POST("/users") create_user() -> JSON {
    $# $RES(201, {"msg": "创建成功", "data": body});
}
写法HTTP 状态码适用场景
$# {...}始终 200普通 JSON 返回
$# $RES(201, {...})指定状态码REST API 语义

错误处理

$throw — 代码级错误传播

$throw 用于终止执行并传播错误，可配合 $try/$catch 捕获：

未捕获 → HTTP 500 + 终端打印错误：

$GET("/boom") boom() -> JSON {
    $throw "something went wrong";
    // 终端: [ERROR] uncaught throw: something went wrong
    // 客户端: HTTP 500 + {"error": "uncaught throw: something went wrong"}
}

用 $try/$catch 捕获，主动返回响应：

$GET("/safe") safe() -> JSON {
    $try {
        $throw "inner error";
    } $catch e {
        $# {"caught": e};
    }
}

$>>ERR — 终端日志（不影响响应）

$GET("/debug") debug() -> JSON {
    $>>ERR("debug info");     // 仅输出到终端
    $# {"ok": true};          // HTTP 响应正常返回
}
